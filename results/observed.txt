Observed 2026-11-07. Steam Frame and a control laptop (MacBook) both associated to the
same AP+BSSID (SSID redacted; NETGEAR, ch149 / 5745 MHz, 80 MHz HE). Flood/ping target is
a WIRED desktop on the same LAN (Realtek 2.5GbE, 1 Gbps). Frame<->wired target and
Mac<->wired target are each a single wireless hop. Same tool, same target, back to back.

  Associated TX PHY rate while idle: HE-MCS 3..6, NSS 2, 80 MHz (288-648 Mbit nominal)

THE FINDING: the Frame's UPLINK collapses under simultaneous RX (bidirectional load),
which is exactly the streaming workload. Each direction alone is fine.

  SINGLE DIRECTION (one at a time)
    Frame uplink only   (UDP flood Frame->wired)    : 40 - 145 Mbit/s  (varies run to run)
    Frame downlink only (UDP flood wired->Frame)    : ~90 Mbit/s       (healthy)

  BIDIRECTIONAL, same tool, concurrent up+down:
    client   uplink (concurrent)   downlink (concurrent)
    Mac      806 Mbit/s            150 Mbit/s      << sustains ~950 Mbit/s total, no collapse
    Frame    3.8 Mbit/s            60  Mbit/s      << uplink dies the moment RX is active

  The decisive control: the Mac, on the SAME AP, SAME wired target, SAME tool, carries
  full bidirectional traffic. The Frame, identical setup, drops its uplink to single
  digits. So the fault is the Frame's radio, not the router, the path, or the method.

  Earlier worst case: under bidirectional load the Frame uplink was measured as low as
  ~5-9 Mbit/s averaged (per-second samples hitting 1-2 Mbit/s). "~8 Mbit/s" was a true
  worst-case bidirectional measurement.

RULED OUT (each with a measurement)
  - Router / path / test method : the Mac control is perfect on the identical setup.
  - Rate control                : `iw dev wlan0 set bitrates` is ignored; firmware-owned.
  - HWSCH hardware scheduler     : hwsch_reset_count stays FLAT (8 -> 8) through the entire
                                   collapse; hwsch_misaligned_offset climbs even during
                                   HEALTHY 140 Mbit/s TX, so it is a benign counter, not the
                                   fault. (This corrects an earlier draft that blamed it.)
  - Firmware crash / recovery    : none this boot (uptime ~32 h, no coredump, no mhi reset,
                                   no "time out while waiting for fw stats done").
  - Driver TX errors             : zero over 30 h incl. load; even full DP_TX debug logs
                                   only clean RX, no ring-full, no descriptor exhaustion.
  - Signal/channel/thermal/PCIe/power-save/BT-coex/scanning/ASPM : each measured, none it.

MECHANISM (as far as evidence reaches)
  The collapse is specifically the TX path losing to the RX path under concurrent load:
  bidirectional, the Frame's UPLINK craters (3.8 Mbit/s) while its downlink still runs
  (60 Mbit/s). A TX-vs-RX arbitration failure in the WCN7850 as configured on the Frame.
  The exact firmware site is not statically recoverable: amss.bin is a dlpager-paged,
  ROM-patching, QSHRINK-logged image (string->code pivots return zero refs), the same hard
  ceiling documented for the wake-on-LAN trace on this device.

RELATED: ValveSoftware/SteamOS issue #2831 (same chip, same firmware build) reports a
crash-then-degrade variant on 6 GHz/160 MHz. Ours reproduces on demand with no crash.

REPRO: see repro/ . Associate the Frame and a healthy control client to the same AP, pick
a wired target, and run up/down/both for each. The "both" phase is the test.
